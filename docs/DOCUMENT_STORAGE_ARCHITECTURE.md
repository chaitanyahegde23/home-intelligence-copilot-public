# Private Document Storage and Metadata Architecture

## Status and scope

This document is the HIC-019 design contract for later household-document ingestion. It chooses storage, lifecycle, provenance, and migration boundaries before sensitive files are accepted.

HIC-019 adds no upload endpoint, document table, migration, parser, extractor, OCR, retrieval, embedding, or AI behavior. HIC-020 must implement only the bounded upload, metadata, storage, and deletion subset described here.

## Deployment and ownership assumption

The current application is a local/private, single-household installation operated by a trusted household administrator. Until HIC-024 and HIC-025 implement authentication and household isolation:

- all stored documents belong to the one deployment household;
- document APIs must bind to loopback or remain behind a trusted private network boundary;
- the application must not claim that filenames, UUIDs, or storage keys provide authorization;
- public internet or multi-user deployment is unsupported;
- sharing a database or storage root between households is prohibited.

HIC-025 introduces the authoritative `households` ownership model and a non-null `household_id` foreign key on document metadata. Its migration creates one bootstrap household and deliberately backfills every existing local document. Every document query, tool, deletion, extraction, and retrieval operation now uses the server-derived household scope. A nullable household boundary is not an acceptable steady state.

## Initial supported document type

The first supported type is a standard, unencrypted PDF with media type `application/pdf` and extension `.pdf`.

HIC-020 must validate the extension, browser/server media type, PDF signature and structure, configurable byte limit, configurable page limit, and absence of encryption before permanent storage. A default maximum of 20 MiB and 500 pages is appropriate for the local MVP. Both values remain server-authoritative and positive. Password-protected, encrypted, malformed, polyglot, active-content-dependent, and unsupported files fail closed.

The repository may contain only independently created synthetic PDFs. Real bills, receipts, policies, warranties, statements, names, addresses, account numbers, and document-derived text remain outside source control, fixtures, logs, screenshots, evaluations, and issue attachments.

## Storage decision

### Metadata

PostgreSQL is authoritative for document metadata and lifecycle state. Database rows never contain the original PDF bytes.

### Original bytes

The initial blob backend is a small storage adapter backed by a private filesystem root:

- local-development host path: `data/documents/`;
- container path when implemented: `/var/lib/home-intelligence/documents`;
- production path: an operator-selected private mounted volume outside the application image and repository.

The root must be configurable, resolved to an absolute path at startup, created with least-privilege permissions, and must not be served as a static directory. The API streams authorized content through application code.

An object is addressed only by an application-generated opaque storage key such as `objects/ab/cd/<uuid>`. Original filenames, user input, hashes, document titles, and URL path segments never participate in filesystem path construction. The adapter must resolve and verify that every final path remains under the configured root and must reject symlinks and traversal.

The storage interface must support write-to-staging, atomic promotion, open/read, existence check, and idempotent delete. A future private object-store adapter may implement the same interface; object-store support is not part of HIC-020.

## Encryption and transport assumptions

- Application-level content encryption is not implemented initially.
- Production operators must place both PostgreSQL and document blobs on encrypted-at-rest volumes, or use an approved object store with server-side encryption.
- Development storage may be unencrypted and therefore must contain synthetic data only unless the operator knowingly accepts local-device risk.
- Remote traffic requires TLS at the deployment boundary. Remote deployment is unsupported until authentication exists.
- Encryption keys, database credentials, and storage credentials belong in environment/secret management and never in PostgreSQL document rows, filenames, logs, or source control.
- Encryption at rest does not replace authorization, deletion, backup protection, or log redaction.

## Proposed metadata model

HIC-020 should introduce a `documents` table with the following contract:

| Field | Purpose and constraint |
| --- | --- |
| `id` | UUID primary key generated by the application. |
| `status` | Required lifecycle enum: `pending`, `stored`, `deleting`, or `failed`. Extraction-specific states belong to HIC-021. |
| `original_filename` | Required normalized display value, bounded to 255 characters; never a path. |
| `media_type` | Required reviewed media type; initially only `application/pdf`. |
| `size_bytes` | Required positive integer bounded by the configured upload limit. |
| `sha256` | Required lowercase 64-character SHA-256 digest of the exact original bytes. |
| `storage_backend` | Required versioned backend identity, initially `private_filesystem_v1`. |
| `storage_key` | Required unique opaque key generated by the application; never supplied by a client. |
| `source` | Required provenance enum, initially `user_upload`. |
| `created_at`, `updated_at` | Required timezone-aware timestamps. |
| `failure_code` | Optional bounded non-sensitive code for a failed lifecycle transition; no raw exception or content. |

Within a household, `(sha256, size_bytes)` identifies an already stored original. HIC-020 rejects a duplicate upload with a structured reference to the existing document rather than storing a second blob. HIC-025 makes this uniqueness rule household-scoped.

The `documents` model deliberately does not store raw bytes, absolute host paths, extracted text, prompts, model output, secrets, document contents, or an account/address inferred from the PDF. HIC-021 stores extracted text only in separate versioned child tables without modifying the original blob.

### Migration plan

1. HIC-020 creates the lifecycle enum, `documents` table, constraints, unique storage key, checksum/size duplicate constraint, status indexes, and reversible Alembic migration.
2. The migration creates schema only; it does not scan a directory or import pre-existing files.
3. HIC-021 adds extraction runs and page/section spans in separate child tables keyed to `document_id` with cascade deletion.
4. HIC-025 creates `households`, adds nullable ownership columns only during the transactionally controlled backfill, assigns the bootstrap household, makes ownership non-null, replaces global duplicate uniqueness with household-scoped uniqueness, and adds household-leading indexes.

## Upload and consistency boundary for HIC-020

PostgreSQL and a filesystem cannot share one atomic transaction. HIC-020 must use an explicit compensating workflow:

1. Stream the request to a newly generated staging key while enforcing the byte limit and computing SHA-256 incrementally. Never load an unbounded file into memory.
2. Validate the complete PDF before promotion. Invalid content deletes the staging object and creates no database row.
3. Insert a `pending` metadata row after duplicate detection.
4. Atomically promote the staging object to its opaque final key on the same filesystem.
5. Change the row to `stored` and commit.
6. If the database commit fails after promotion, delete the promoted object. If compensation fails, emit a privacy-safe orphan identifier for reconciliation, not a filename or content.

Only `stored` documents are readable or eligible for extraction. A startup/maintenance reconciler should remove stale staging objects and flag missing or orphaned final objects without logging sensitive metadata.

## Deletion contract

Deletion is explicit, idempotent, and deny-first:

1. Change a stored row to `deleting` and commit so reads, extraction, retrieval, and AI use stop immediately.
2. Delete the original blob and every derived extraction/chunk artifact. Missing objects count as already deleted.
3. Hard-delete the document row and cascade child metadata in a database transaction.
4. Retain only a privacy-safe audit event containing the document UUID, household/audit actor when available, outcome, and timestamp. Do not retain filename, checksum, content, extracted text, or storage key.
5. If storage deletion fails, leave the row in `deleting`, return a visible retryable failure, and retry idempotently. Never restore read access automatically.

Deleting a document does not immediately erase copies already present in an operator-managed backup. Backup retention and restore behavior below make that limitation explicit.

## Retention and backups

- Original documents are retained until the household explicitly deletes them; there is no silent age-based deletion in the initial product.
- Failed or incomplete staging objects must be purged automatically after at most 24 hours.
- The application does not create document backups in HIC-020.
- If production backups are enabled, database metadata and blobs must be backed up as one documented recovery set, encrypted in transit and at rest, access-restricted, and retained for no more than 30 days by default.
- A deletion ages out of encrypted backups at the configured retention boundary. This limitation must be visible to the user/operator.
- A restore procedure must reconcile database rows and blobs, replay or honor deletion audit events newer than the restored snapshot, and verify checksums before declaring recovery complete.
- Backups, restored copies, and diagnostics must never be committed or attached to GitHub, Linear, test reports, or support conversations.

## Threat model

| Threat | Required control |
| --- | --- |
| Path traversal, absolute paths, or crafted filenames | Opaque server-generated storage keys; resolved-root containment; filename never used as a path. |
| Symlink or race-based escape | Private root, no client-created directories, reject symlinks, atomic same-volume promotion. |
| Oversized files or parser denial of service | Streaming byte limit, page limit, time/resource bounds, parse only after bounded receipt. |
| MIME spoofing, polyglots, malformed or encrypted PDFs | Extension/media/signature/structure agreement and fail-closed parser validation. |
| Duplicate or replayed upload | Exact streaming SHA-256 plus size, single-household uniqueness, structured duplicate response. |
| Partial database/filesystem state | Lifecycle state machine, compensation, idempotent deletion, and orphan reconciliation. |
| Unauthorized or cross-household access | Local singleton boundary now; authenticated non-null household scoping before remote/multi-user use. |
| Sensitive logs and errors | Stable failure codes and opaque UUIDs only; never log filename, content, checksum, extracted text, or raw parser exceptions. |
| Backup or snapshot leakage | Encrypted restricted recovery sets, bounded retention, documented restore and deletion behavior. |
| Malicious instructions embedded in documents | Treat extracted text as untrusted data; never allow it to alter system instructions, tool allowlists, authorization, or citation requirements. |
| Checksum enumeration | Do not expose global lookup-by-hash; duplicate results are available only inside the authorized household scope. |

## Provenance contract

The original immutable PDF is the root of document provenance. Its document UUID, exact byte checksum, size, media type, original display filename, storage backend/version, storage key, source, and timestamps identify the stored artifact.

HIC-021 extraction records retain extractor name/version, processing timestamps, document checksum, page/section numbers, character offsets into exact extracted page text, and text checksums. HIC-022 chunks and HIC-023 citations must trace through those records to the immutable original. Reprocessing under a new extractor version creates a new derivative and never overwrites the original blob.

## HIC-020 implementation conformance

HIC-020 implements the bounded original-file contract through `Document` and
`DocumentDeletionAudit` models, a reversible Alembic migration, `PrivateDocumentStorage`, and
thin `/documents` routes. It streams uploads through a size-limited SHA-256 calculation, requires
an ordinary `.pdf` filename and exact PDF media type, parses strictly, rejects encryption,
zero-page/over-limit documents, JavaScript, embedded files, catalog actions, traversal, symlinks,
and duplicate checksum/size pairs, and promotes only server-generated opaque keys. Database or
storage failures roll back and compensate promoted/staged objects. Deletion moves metadata to a
non-readable state before idempotently removing the blob and retaining a content-free audit row.
Extraction, OCR, download, staging reconciliation, object stores, retrieval, AI, authentication,
and household scoping remain outside HIC-020.
